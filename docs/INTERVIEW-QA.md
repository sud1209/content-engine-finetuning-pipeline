# Technical Interview Q&A — Content Engine Fine-Tuning Pipeline

---

## 1. Architecture & Purpose

**Tell me about this project. What does it actually do?**

So the starting point was a Twitter content engine that scores tweet drafts before they get published — it calls Claude Haiku for every score, which costs money and adds latency. The idea here was: can we train a local model to replicate what Haiku does, so we can remove that API dependency entirely? This repo is the full pipeline for that — synthetic dataset generation, QLoRA fine-tuning on Llama 3.1 8B, and then rigorous benchmarking to see how close we actually got.

**Walk me through the pipeline stages end to end.**

Sure. Stage one is dataset generation — I used Claude Sonnet via the Claude Code subscription to generate 2,355 scored tweet examples, which cost nothing beyond the subscription. Stage two is ground truth — I used the Haiku API directly to score 200 held-out examples. Those become the benchmark target because Haiku is the model I'm trying to replace. Stage three is splitting the dataset and pushing it to HuggingFace Hub. Stage four is QLoRA fine-tuning on a Kaggle T4 GPU — free compute, about six hours total. Stage five is benchmarking — three-way comparison, fine-tuned vs base Llama vs Haiku ground truth, on those 200 held-out examples.

**Why Claude Haiku specifically for the ground truth?**

Because Haiku is what the production system uses. If I'm trying to replace Haiku, I need to measure how close my model gets to Haiku's outputs — not Sonnet's, not GPT-4's. This also turned out to be one of the more interesting findings: training labels were generated by Sonnet and ground truth came from Haiku, and those two models apply the same rubric differently. That label bias is a real reason the fine-tuned model underperforms on judgment-heavy dimensions.

## 2. The Scoring Rubric

**Explain the scoring rubric. What are you actually measuring?**

There are six dimensions. Hook strength at 25% weight — this uses Harry Dry's three-test framework: is the claim visualizable, falsifiable, and something nobody else can say? Tone compliance at 20% — six hard rules: zero hashtags, no em-dashes, no exclamation marks, no hedging, no banned words like "transformative" or "ecosystem." X algorithm optimization at 20% — models how X weights engagement, replies count 27x, so debate-bait plus data scores high. Data specificity at 15% — named people, tools, real numbers. Pillar alignment at 15% — the content topic has to be clear in the first sentence. And CTA quality at 5% — top-of-funnel, awareness-style calls to action score high; hard sells score low.

**What's the `never_list_violation` flag and why does it wipe the composite score to zero?**

It's a binary flag — if a hashtag appears anywhere in the tweet, it fires. And when it fires, the composite score becomes zero regardless of every other dimension. The reasoning is that hashtags are an absolute disqualifier for this content strategy — not a soft preference, not a dimension to score down, a hard constraint. Letting a model learn to compensate for a hashtag with high scores elsewhere would undermine the whole rubric. The Pydantic validator also forces `tone_compliance` to zero when this flag fires, because zero hashtags is literally one of the six core tone rules.

**Why is tone compliance scored zero through ten but everything else one through ten?**

Every other dimension has some floor — even a terrible tweet has some degree of hook, some degree of data specificity. But tone compliance can legitimately be zero: a tweet with a hashtag has broken the most fundamental rule, and giving it a one would be dishonest. The validator enforces the coupling both ways — tone compliance zero is only valid when there's a hashtag violation, and a hashtag violation always sets tone compliance to zero.

**Walk me through the composite score formula.**

It's a weighted average of the six dimensions — the weights sum to 100 so it's literally weighted percentage. Then there's a `+ 0.5` before rounding. That's not arbitrary — Python's default rounding is banker's rounding, which rounds 8.5 to 8. The 9.25 threshold for the "ready" tier means a tweet that scores 9.0 composite is not publishable, but small errors in rounding near that boundary could produce inconsistent results. The `+ 0.5` forces consistent round-half-up behavior across the rubric.

**You mentioned three quality tiers. What are they?**

Ready is 9.25 and above — publishable as-is. Below target is 8.0 to 9.24 — needs revision. Failed floor is anything below 8.0 — fundamental quality failure, rewrite required. The 9.25 threshold is quite high intentionally. A tweet that scores a 9 on all six dimensions only gets a 9.0 composite, which isn't ready — near-perfect across all dimensions is required.

**What is the rubric hash and why does it exist?**

Every scored example stores the first eight characters of the SHA-256 hash of the scoring system prompt. When new training examples are ingested, the hash is validated against the current prompt. If the rubric has changed — new banned word, updated weight — the hash changes, and any stale examples get rejected at ingest time. Without this, you could silently mix examples scored under different rubrics, which would add label noise the training loop has no way to detect.

## 3. Dataset Engineering

**How does the chat template formatting work and why does it matter?**

Each training example becomes a three-turn messages list — system prompt, user message with the tweet, and an assistant response with the JSON scores. SFTTrainer needs a string column, not a list of dicts. So during data loading I apply the Llama 3.1 Instruct chat template via `tokenizer.apply_chat_template` with `add_generation_prompt=False`. That last flag is critical — without it, the template appends the assistant turn header, which would tell the model "now you generate," but in training mode that header should not appear in the target. That was actually a bug that caused silent training failures early on.

**Walk me through what `validate_dataset.py` checks.**

It checks JSON parse errors, Pydantic schema violations, examples where all six scores are identical — which usually means low-effort labeling — reasoning strings shorter than 20 words, and it verifies that `never_list_violation` is consistent with the actual tweet content. The pass/fail criteria are at least 2,000 valid examples and all three quality tiers represented. If any tier is missing, the model won't learn to discriminate between quality levels. It exits with code 1 on failure so it can gate CI pipelines.

**What was the root cause of the underperformance on judgment dimensions?**

Two things compound each other. First, template repetition — batches 9 through 28, which is 1,440 of the 2,355 examples, used a 20-tweet template cycle. The same tweet content appeared across multiple batches with slightly varied scores. The model learned to associate content fingerprints with scores rather than applying the rubric logic. A model that's memorized "this tweet gets a seven" generalizes badly to new content.

Second, Sonnet/Haiku bias. Training labels came from Sonnet, ground truth from Haiku. They apply the same rubric differently — Sonnet is more conservative on CTA quality and more generous on hook strength. The fine-tuned model learned Sonnet's calibration and gets penalized when evaluated against Haiku's calibration.

## 4. QLoRA Fine-Tuning

**Why LoRA instead of full fine-tuning?**

Full fine-tuning of an 8B model needs about 80GB of VRAM in fp16 — the Kaggle T4 has 15GB. LoRA adds small adapter matrices to frozen base layers, reducing trainable parameters from 8 billion to about 67 million. Combined with 4-bit quantization of the frozen weights, the whole thing fits in around 12GB. There's essentially no accuracy penalty for task adaptation tasks like this, and you can merge the adapter back into the base weights afterwards for zero-overhead inference.

**What does rank 16 mean and why that number?**

The rank controls the capacity of the adapter. Each targeted layer gets two matrices, one of shape `hidden_dim × rank` and one of `rank × hidden_dim`. Rank 16 gives you about 917,000 trainable parameters across all seven target modules. Higher rank means more capacity to model complex patterns but also more risk of overfitting on a small dataset like this. Rank 16 is the standard starting point for task adaptation. The potential improvement I documented is using rank 32 or 64 for the judgment-heavy dimensions — they require more nuanced reasoning than a binary rule like hashtag detection.

**What is lora_alpha and how does it relate to rank?**

Alpha is a scaling factor — the adapter's contribution is scaled by `alpha / rank` before being added to the frozen layer output. With alpha 32 and rank 16, the effective scale is 2.0. The reason you often see alpha set to twice the rank is that it keeps the effective learning rate of the adapter independent of the rank value. If you change rank without adjusting alpha, you've effectively changed the learning rate, which is rarely what you want.

**Why target all seven projection layers?**

The seven are the four attention projections — q, k, v, o — and the three MLP projections — gate, up, down. Adapting only attention is a common default but it limits the model's ability to adjust its feedforward representations, which is where a lot of the output style and factual calibration lives. Scoring tweet quality requires both — attention adjustments to focus on the right features of the tweet, and MLP adjustments to map those features to score values. Targeting all seven costs more trainable parameters but produces better task adaptation.

**Walk me through the T4 training constraints.**

The T4 has 15GB VRAM and is a Turing-class GPU, CUDA capability sm_75. That has two implications. First, bf16 requires Ampere or newer — sm_80 plus — so bf16 is off and fp16 is on. Second, batch size has to be 1 because a larger batch OOMs. I compensate with gradient accumulation of 16, so the effective batch size is 16 — gradients accumulate across 16 forward passes before a weight update. Also, P100 is completely incompatible because PyTorch 2.2 dropped support for sm_60, the P100's compute capability. The notebook has an explicit GPU guard that raises immediately if it detects P100.

**What does Unsloth contribute?**

Optimized CUDA kernels — particularly for flash attention and RoPE position embeddings — and a more memory-efficient gradient checkpointing strategy. The result is roughly a 2-5x speedup over vanilla PEFT plus SFTTrainer on the same hardware. On a six-hour Kaggle session, that's the difference between completing training with time to spare and hitting the session limit mid-run.

**What does packing do and why is it important on T4?**

Most tweet scoring examples are 200-400 tokens. Without packing, each is padded to 2048 tokens — you're wasting 80%+ of each sequence on padding. Packing concatenates multiple examples end-to-end with EOS tokens between them to fill the full 2048-token context. One training step processes multiple real examples instead of one padded example. On T4 where every batch is size 1, this is especially important for utilization — you want the GPU doing real work on every forward pass.

## 5. Benchmark Evaluation

**Why MAE as the primary metric instead of accuracy?**

Exact accuracy is too strict for a 1-to-10 scoring task. A prediction of 7 when the answer is 8 is nearly right, but accuracy counts it as completely wrong. MAE measures actual error magnitude — an MAE of 0.5 means you're off by half a score point on average, which is meaningful and actionable. I also report `within_1_agreement`, which is the fraction of predictions within one point of ground truth. That's the practical usability metric — within-one is acceptable for most publishing decisions.

**Walk me through all the metrics you compute.**

Per dimension: MAE, exact agreement, within-1 agreement, and Pearson correlation. At the aggregate level: mean MAE across all six dimensions, mean within-1 agreement, composite score MAE, tier accuracy — which is whether you predicted the right tier rather than the right exact score — never-list F1, and mean inference latency.

**Why compute Pearson correlation in addition to MAE?**

They tell you different things. MAE tells you error magnitude. Pearson tells you whether the model's rankings are consistent with ground truth rankings. A model could have low MAE but poor correlation — consistently off by a constant bias — or high MAE but good correlation — correct ordering but miscalibrated scale. For publishing decisions, ranking matters more than absolute calibration. If one tweet scores higher than another in ground truth, the model should rank them the same way even if the absolute values are off.

**The fine-tuned model has a higher mean MAE than the base model. How do you explain that?**

That's the most honest part of this project. The fine-tuned model is worse than zero-shot on the judgment dimensions, and the reason is training data quality — specifically the template repetition I mentioned. The model memorized score patterns for specific content templates. The base model applies rubric logic from its pretraining, which, even without fine-tuning, generalizes better than memorized patterns. The win for the fine-tuned model is `never_list_f1 = 1.0` — perfect hashtag detection — because that's a binary rule that's easy to learn consistently.

**Explain the never-list F1 result.**

F1 is the harmonic mean of precision and recall. A score of 1.0 means perfect precision — every time the model predicts a hashtag violation, there's actually a hashtag — and perfect recall — every actual hashtag violation is caught. That's the highest-stakes binary decision in the rubric. A false negative, missing a hashtag, would let a tweet with a hashtag reach publishing review with a non-zero composite score. The fine-tuned model got this exactly right.

**How did you handle models that output shortened key names?**

Some models output `algorithm_optimization` instead of `x_algorithm_optimization`, or `hook` instead of `hook_strength`. I built a `KEY_ALIASES` dict mapping each canonical key to its known aliases, and a `normalize_result` function that checks for aliases whenever a canonical key is missing. If an alias is found, it's renamed. If nothing matches, the dimension defaults to 5.

This came up because the base Llama 3.1 8B consistently dropped the `x_` prefix, which caused a `KeyError` on the first benchmark run. And the actual saved `benchmark_results.json` had two unique typo variants — `x_algorithm_optivation` in one fine-tuned result and `x_algorithm_optification` in one base result — which required normalizing the saved file with a fuzzy prefix match before computing metrics.

## 6. Production Serving

**Describe the serving architecture.**

FastAPI fronts a vLLM inference server. vLLM handles model loading and token generation; FastAPI handles request validation, rate limiting — 100 requests per minute per IP — response formatting, and cost tracking. They communicate over HTTP, FastAPI uses an async OpenAI client pointing at vLLM's OpenAI-compatible endpoint. vLLM is configured with the fine-tuned model, dtype float16, max sequence length 2048.

**What is guided JSON decoding and why does it matter?**

It constrains the token sampling process so vLLM can only produce tokens that are valid continuations of the target JSON schema. At each step, a mask is applied to the vocabulary — only tokens that advance the JSON state machine toward a valid score object are allowed. The model physically cannot produce malformed JSON or invalid field names. In standard sampling, you need defensive parsing, retry logic, fallback defaults. With guided decoding, you get valid JSON every time — no retries, no fallbacks.

**How does your batch endpoint handle failures?**

It uses `asyncio.gather` with `return_exceptions=True`, which captures exceptions as values in the result list rather than propagating immediately. Then it re-raises the first exception it finds. So it's all-or-nothing — either all scores in the batch succeed, or the whole batch fails with a meaningful error. I chose this over partial results because partial score sets are hard to consume correctly in the downstream pipeline.

**How do you track cost?**

SQLite database, one row per request. I log timestamp, latency in milliseconds, composite score, model version, and estimated cost. The cost formula is latency in seconds times the per-second cost of an AWS g5.xlarge — that's an A10G 24GB at about a dollar per hour on-demand. Every request maps directly to GPU wall-clock time. There's a weekly summary function that aggregates totals. Logging is best-effort — database errors are swallowed so a logging failure never blocks a scoring request.

## 7. Post-Training Pipeline

**What is the eval gate before pushing a new adapter?**

Before pushing, the script fetches the currently published model card on HuggingFace Hub and extracts the mean MAE from its metadata. If the new adapter's mean MAE is more than 0.05 worse than the published version, the push is blocked. This prevents a bad training run from silently replacing a better model. The 0.05 tolerance accounts for natural variance between benchmark runs. There's a `--force` flag that bypasses the gate when regression is intentional — like when retraining on a new rubric version.

**Why merge the LoRA adapter before GGUF export?**

LoRA inference requires computing `base_output + A × B × scale` at each adapted layer, which adds computational overhead and requires the PEFT library at runtime. Merging fuses the adapter into the base weights — `W_merged = W_base + (A × B × scale)`. The result is a standard transformer with no adapter overhead. GGUF export requires a fully merged model because llama.cpp doesn't support LoRA adapters at inference time.

**Walk me through GGUF export.**

Two steps. First, convert — `convert_hf_to_gguf.py` from the llama.cpp repo converts the merged HuggingFace safetensors to F16 GGUF. That's a format conversion, weights stay in fp16. Second, quantize — `llama-quantize` compresses to the target format, default Q4_K_M. That's a 4-bit mixed quantization where important matrices get higher precision. An 8B model goes from about 15GB in fp16 to about 3GB in Q4_K_M. Then you can run it locally with Ollama — `ollama create tweet-scorer --file tweet-scorer-q4km.gguf` — no GPU required.

## 8. Failure Modes

**What fails silently in this pipeline?**

The Sonnet/Haiku label bias. The model trains to convergence on Sonnet-labeled data, validation loss decreases, nothing in the training loop signals a problem. The mismatch only surfaces at benchmark time. Without the explicit root cause analysis, you'd see "fine-tuned is worse than base" and assume a training bug rather than a scorer calibration mismatch.

**How do you handle the JSON parse failures from model output?**

Two scenarios. In the benchmark notebook, if JSON parsing fails I fall back to scoring all dimensions at 5, `never_list_violation` false, and reasoning "parse_error." That's a conservative fallback — 5 on everything produces a failed-floor composite, which correctly signals low quality. In the ground truth generation script, Haiku sometimes appended natural language after the JSON, which caused `json.loads` to raise "Extra data." The fix was `json.JSONDecoder().raw_decode(text.strip())`, which parses only the first complete JSON object and ignores trailing content.

**What was the VRAM management issue in the benchmark notebook?**

The T4 has 15GB. Two 4-bit quantized 8B models simultaneously need about 16GB. The solution is sequential loading — score all examples with the fine-tuned model, then `del model`, `gc.collect()`, `torch.cuda.empty_cache()`, then load the base model. All three steps are necessary. `del` removes the Python reference. `gc.collect()` handles reference cycles. `torch.cuda.empty_cache()` returns the freed GPU memory back to the OS. Without all three, PyTorch can hold memory blocks even after the reference is gone.

## 9. If You Were Doing This Again

**What's the single most impactful thing you'd change?**

Regenerate batches 9 through 28 with unique tweet content per example. That's 61% of the training set with template repetition — it's the primary reason judgment dimensions underperform. One concrete approach: generate tweet drafts from real AI/ML news headlines, then score those. No two training examples share a content template. The dimensions that require rubric-based generalization — CTA quality, X algorithm optimization — would see the largest improvement.

**Would you use chain-of-thought in the training format?**

Yes, and it's actually straightforward — the reasoning field already exists in every training example. Right now the training format is `tweet → scores`. Reformatting to `tweet → reasoning → scores` lets the model learn to apply rubric logic step by step before committing to numbers. That's the difference between training on worked solutions versus just answers. It only requires changing how `split_dataset.py` constructs the assistant turn — move reasoning before the score JSON.

**Is GRPO the right next step after better SFT data?**

Once SFT convergence improves, yes. GRPO can directly optimize for Haiku agreement — the reward signal is straightforward: composite MAE between model output and Haiku ground truth, with a penalty for never-list mismatches. But you need a working base policy first. Applying GRPO to the current model would just amplify the template memorization. The sequencing matters: better training data, then better SFT convergence, then GRPO to squeeze the remaining gap.

**What would relabeling the training data with Haiku cost?**

About two dollars. 2,355 examples, each needs a system prompt plus tweet content plus score output — roughly 650 tokens per example. About 1.5 million tokens total. At Haiku's pricing that's around $1.40 input plus $0.57 output. That eliminates the Sonnet/Haiku label bias entirely and aligns the training distribution with the benchmark distribution. It's probably the highest ROI dollar spent in the whole pipeline.
